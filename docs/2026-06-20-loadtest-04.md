## 테스트 목적

4차 테스트는 공개 GET API 기준선을 다시 확인한 뒤, 짧은 시간 안에 Spike와 Stress 부하를 걸어 서버가 5xx 오류 없이 안정적으로 응답하는지 확인하는 것이 목적이다.

이전 2차 테스트가 공개 GET API의 기본 부하 흐름을 확인했고, 3차 테스트가 문제은행 조회 API에 집중했다면, 이번 테스트는 같은 공개 API 묶음을 기준선, 급상승, 단계 상승 세 가지 상황으로 나누어 비교했다.

## 결과 해석

공개 GET API 기준으로는 최대 150 VU까지 5xx 오류와 HTTP 실패 없이 응답했다. 세 시나리오 모두 checks 100%, http_req_failed 0.00%를 유지했고, p95 응답 시간도 한 자릿수 ms 범위에 머물렀다.

이번 결과는 로컬 환경의 공개 GET API 중심 테스트이므로 운영 환경 전체 성능을 보장하지는 않는다. 다만 기준선, 급상승, 단계 상승 상황에서 서버가 안정적으로 응답하는지 확인하는 목적에는 충분한 근거를 제공한다.

## Keep / Problem / Try

### Keep

- 공개 GET API 기준선을 최신 경로 기준으로 다시 정리했다.
- Spike와 Stress 시나리오를 분리해 부하 형태별로 비교할 수 있게 했다.
- k6 결과를 Prometheus와 Grafana로 전송해 영상에서 지표 변화를 함께 확인했다.
- 영상 파일은 Git 저장소에 포함하지 않고 블로그 업로드 자료로만 관리한다.

### Problem

- 로컬 노트북 환경이라 운영 서버와 동일한 네트워크, CPU, DB 조건은 아니다.
- GET 중심 테스트라 쓰기 API, 로그인, Socket.IO 실시간 기능까지 검증한 것은 아니다.
- 30분 Soak 테스트는 이번 회차에서 실행하지 않았다.

### Try

- 30분 Soak 테스트를 별도 실행해 장시간 안정성을 확인한다.
- 인증 API와 요청 제한 로직을 분리해 부하 테스트한다.
- Socket.IO 멀티플레이 흐름은 별도 도구 또는 별도 k6 시나리오로 검증한다.
- 쓰기 API 테스트는 로컬 DB 백업과 복구 절차를 먼저 준비한 뒤 진행한다.
