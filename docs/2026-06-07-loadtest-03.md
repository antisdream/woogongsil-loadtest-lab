## 테스트 목적

3차 테스트는 우공실의 핵심 기능인 문제은행 조회 API를 대상으로 진행했다.

앞선 전체 GET 테스트는 홈 화면, 화면 설정, 게시판, 회식맵 등 여러 API를 넓게 확인하는 목적이었다. 이번 테스트는 필기·실기 문제 조회 API에 집중해 p95, p99 응답 시간과 실패율을 확인하는 데 목적이 있다.

## 테스트 전 확인한 문제

처음에는 `sessionToken`을 query 또는 header로 전달했지만 API가 401로 응답했다.

브라우저 Network 탭을 기준으로 확인한 결과, 실제 성공 요청은 Cookie header를 포함하고 있었다. 따라서 k6 테스트에서도 브라우저 요청과 동일하게 Cookie 값을 환경변수로 전달하는 방식으로 정리했다.

Cookie 값은 테스트 실행 환경에서만 사용하며, 결과 파일과 저장소에는 남기지 않는다.

## 결과 해석

최대 50명의 가상 사용자가 문제은행 관련 GET API를 반복 조회했고, 전체 요청 31,320건 중 실패 요청은 발생하지 않았다.

k6 기준 p95 응답 시간은 약 157.59ms, p99 응답 시간은 약 214.66ms로 측정되었다. 로컬 환경 기준으로 문제은행 조회 API는 50 VU 규모의 GET 부하에서 안정적으로 응답하는 것을 확인했다.

## Keep / Problem / Try

### Keep

- 운영 서버가 아니라 로컬 서버에서만 테스트했다.
- GET 요청만 사용해 DB 변경 위험을 줄였다.
- 실제 브라우저 요청과 동일한 Cookie 인증 조건을 적용했다.
- k6 결과를 Prometheus로 전송하고 Grafana에서 시각화했다.
- 5xx Error Rate와 HTTP Failed Rate가 모두 0%로 유지되었다.

### Problem

- `sessionToken`만 전달했을 때는 401이 발생했다.
- 브라우저 요청 구조를 확인하기 전까지 인증 방식이 맞지 않았다.
- 단순 전체 GET 테스트만으로는 문제은행 API 성능을 정확히 보기 어려웠다.

### Try

- 회식맵 POST 테스트를 진행할 경우 로컬 DB 백업과 더미 데이터 삭제 전략을 먼저 준비한다.
- Socket.IO 멀티플레이 테스트는 Artillery를 사용해 별도 시나리오로 분리한다.
- 장기적으로 Node.js 백엔드에 `/metrics` 엔드포인트를 추가해 CPU, 메모리, 이벤트 루프 지연도 함께 관찰한다.
- 패치 전후 같은 조건의 k6 테스트를 반복해 성능 변화량을 비교한다.
